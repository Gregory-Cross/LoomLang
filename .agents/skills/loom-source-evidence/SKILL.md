# Source-supported evidence

Start from a named question or proposed claim, exact source identities and a
bounded reference set. Locate decisive passages by full path and symbol/range;
same-named helpers are distinct. Separate what the source states, what follows
by inference, and what remains unknown. Search hits only locate candidates.

For extraction, preserve units, qualifiers and omitted counts; do not convert
an inventory or a completed-log summary into a correctness or execution claim.
For reports/docs, compare each material claim with its supporting source,
including conditions, exceptions, authority/status and negative examples.
A working link or matching hash is not evidence that the claim is true.

Name the checked reference set and unchecked remainder. An enumerated set of
required answers can support assigned-scope coverage; sampled claim checks
cannot prove full correctness or defect absence. More findings or more prose
are not automatically better evidence. Report contradictions without inventing
adoption, acceptance or implementation status.

Use existing specialized skills when their tasks actually apply:

- [loom-architecture](../loom-architecture/SKILL.md) for selecting compiler or
  semantic authority; stale routing stays unresolved.
- [loom-adversarial-review](../loom-adversarial-review/SKILL.md) for compiler
  caller/type/precharge or closure work. This skill alone does not close it.
- [rust-dependency-source](../rust-dependency-source/SKILL.md) for exact locked
  dependency APIs, subject to the executing role's allowed commands.

These procedures do not widen read/write/command scope. Missing authority,
dependencies or necessary checks must qualify the result or return to the parent.
Output a concise claim-to-source account, relevant counterexamples, checked
scope and unresolved questions; write an artifact only when explicitly assigned.
